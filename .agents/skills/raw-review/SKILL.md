# raw-review

개발 블로그 글을 읽고 독자가 내용을 따라가는 데 걸리는 지점을 찾는다. 기준은
[Anti-Patterns in Software Blogging](https://refactoringenglish.com/blog/anti-patterns-software-blogging/)의
글쓰기 항목이다. 이 기준을 절대적인 규칙으로 적용하지 말고 글의 목적과 예상 독자에 맞춰 판단한다.

## 대상 확인

- 사용자가 지정한 글이나 붙여 넣은 초안을 읽는다. 저장소의 포스트를 지정했다면 해당 `raw/<slug>/index.mdx`만 읽는다. 대상이 모호하면 후보를 확인한 뒤 필요한 경우에만 묻는다.
- 제목과 첫 세 문장, 본문, 링크가 걸린 문맥을 확인한다. 예상 독자나 글의 목적이 명시되어 있으면 이를 기준으로 삼는다. 명시되지 않았다면 글에서 드러나는 범위를 잠정 기준으로 삼고, 그 가정을 결과에 밝힌다.
- 리뷰는 읽기 전용이다. 사용자에게 글 수정까지 요청받은 경우에만 수정 작업을 진행하며, `raw/` 수정에는 저장소의 승인 규칙을 따른다.

## 검사 기준

1. **독자가 얻을 것과 도입**: 제목과 첫 세 문장만 읽어도 이 글이 누구에게 유용하고 무엇을 얻을 수 있는지 알 수 있는가? 배경 설명, 자기소개, 인용문 등이 핵심으로 들어가는 길을 불필요하게 늘리는가? 이야기로 시작하더라도 읽을 이유가 바로 드러나면 문제로 보지 않는다.
2. **사전 지식의 일관성**: 글이 정한 독자에게 생소할 용어·개념·도구를 설명 없이 사용하는가? 이미 아는 개념에 빗댄 설명이 실제 예상 독자에게도 익숙한가? 모든 용어를 초보자 수준으로 설명하도록 요구하지 않는다.
3. **글 안에서 이해 가능성**: 핵심 내용을 이해하려면 외부 링크나 각주를 반드시 열어야 하는가? 필요한 최소 설명을 본문에 담고, 링크는 더 깊이 읽을 자료로 제공하는가?
4. **시리즈의 독립성**: 이전 편을 읽었거나 글쓴이만의 용어를 기억한다고 가정하는가? 현재 글에 필요한 앞선 맥락을 짧게 요약했는가? 연속해서 읽어야 하는 성격의 글이라면 그 필요성이 독자에게 분명한지 살핀다.
5. **문체와 전달력**: 진지해 보이기 위한 불필요한 격식, 수동적인 표현, 상투적인 문구가 뜻을 흐리는가? 글쓴이의 자연스러운 표현이 살아 있는가? 구어체를 강요하거나 AI 작성 여부를 문체만으로 단정하지 않는다.

모바일 화면 넘침, 반응형 레이아웃, 글꼴, 색상 대비 등 표시 환경은 평가하지 않는다. 사실관계 검증이나 출처의 신뢰도 평가는 사용자가 함께 요청한 경우에만 해당 작업으로 다룬다.

## 결과 작성

- 실제로 발견한 문제를 영향이 큰 순서로 제시한다. 각 항목에 **위치 또는 짧은 인용**, **독자가 겪는 어려움**, **구체적인 수정 방향**을 담는다.
- 문제가 아닌 항목을 채우기 위해 지적을 만들지 않는다. 판단이 예상 독자에 따라 달라지면 그 조건을 밝힌다.
- 마지막에 글의 강점과 가장 먼저 고칠 부분을 짧게 정리한다. 문제가 없으면 그렇게 말하고 근거를 적는다.
- 사용자가 수정안을 요청했다면 해당 문장의 간결한 대안을 제시한다. 전체 글을 임의로 다시 쓰지 않는다.
