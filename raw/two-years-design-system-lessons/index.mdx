## 디자인 시스템의 논의가 있기 전

내가 입사했고, 우리팀이 아직 Vue.js를 쓰고 있을 때에 이미 사내에 공용 컴포넌트 라이브러리의 흔적이 있었다. 버튼, Input과 모달 등...
허나 이 컴포넌트들은 잘 쓰이지 않고 있었을 뿐더러 디자이너는 이 공용 컴포넌트의 존재도 알지 못했다.

## 우리는 왜 디자인 시스템을 도입하려 했는가?

사실, 정확히 구분해야하는 것은 우리는 처음부터 디자인 시스템을 원한 것이 아니라, 디자이너와 명확한 소통 방식, 그리고 컴포넌트 라이브러리 도입을 원했다. 개발팀이 겪은 문제는 다음과 같았다.

- 디자인에 의미있는 토큰(primary)이 아니라 raw한 값(hex 혹은 13px 같이)이 들어있었고, 개발자들은 이를 그대로 코드에 박아넣고 있었다. 이는 코드 재활용을 어렵게 만들었다.
- 디자이너 간에도 UI가 통일되지 않아 "기존에 쓰던 카드 말고 이번에 새로 컴포넌트를 만드는거에요?" 혹은 "디자인에 line-height가 1.3이던데 다른 곳은 1.5를 쓰고 있어서요..."와 같이 다시 물어봐야하는 일이 잦았다.

마침 좋은 기회로 우리는 기존 제품을 대체할 리액트 기반의 새 제품 개발에 들어갔고, 나를 포함해 개발팀이 먼저 디자이너들에게 UI 라이브러리의 도입을 제안하게 되었다.

## 어떤 것을 고려했는가?

당시 비즈니스 요구사항은 **빠르게 개발할 것** 이었다. 다음의 고려사항이 있었다.

- 커스텀 없이 바로 사용 가능한 완성형 컴포넌트 라이브러리 일 것
- 커스텀하기 충분히 유연할 것
- Figma를 지원할 것
- 러닝커브가 낮을 것

위 요구사항을 만족하면서 디자이너들의 선택이 더해져 우리가 고른 것은 **Chakra**(당시 v2)였다.
우선 Headless(React Aria, Radix UI 등)를 사용하는 것은 런닝커브가 있는 점, 이를 기반으로 새 UI를 구축해야했기 때문에 탈락했다.
Antd같은 다른 완성형 라이브러리들도 거론되었는데 그들의 디자인 색체가 강하고, 커스텀이 어려워 탈락했다.

## UI 라이브러리 도입은 디자인 시스템 도입이 아니었다

앞서 겪은 문제는 다음과 같았다.

- 시멘틱 토큰이 없어 개발자들이 재활용이 어려웠음
- 디자이너간의 UI가 통일되지 않음

Chakra를 쓰고서 이 문제는 해결되었을까? 결론적으로 그렇지 않았다.
고려하지 못한 요인이 다양하게 있었다.

### Chakra의 도입이 공통된 용어 사용을 보장해주지는 못했다

Chakra도입 이전에 `#fe7e43`로 넘어오던 값을 이제 primary라고 부르게 되었지만 디자인 결과물에는 여전히 `#fe7e43`로 박혀있었다. 개발자들에게도 primary라는 용어가 생소했다. 여전히 디자이너가 준 hex값을 그대로 쓰거나 `orange.500`으로 쓰는 사람도 있었다.

왜 이런 현상이 일어났을까? 당시 우리가 이해하지 못했던 것은 디자인 시스템이란 **디자이너간의 합의로 만들어지는 언어 체계라는 것** 그리고 더 나아가 **개발자와 디자이너가 동일한 이해를 구축하는 것**이다. 이건 단순히 라이브러리를 도입한다고 형성되는게 아니다. 디자이너와 개발자가 끊임없이 소통하며 시간을 쏟아 천천히 쌓아 올려야하는 것이다.

### 디자인 시스템이 모든 디자인을 통일해주는 것은 아니었다

제품의 특성상 화면은 계속 새로 만들어졌고, 다양한 형태의 UI 시도가 많이 일어났다.
